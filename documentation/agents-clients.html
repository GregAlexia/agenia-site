Variante n8n + Twilio : personnaliser un agent WhatsApp ou un chatbot pour un client

Comment décliner un même agent (n8n + Twilio) sur le contexte d'un client : quoi lui demander, où le ranger, comment l'injecter dans l'agent, et comment le recetter avant la mise en ligne. Version du 24/11/2026.

Variante, pas la méthode de Léo. L'agent Léo d'AgenIA est une application Python branchée directement sur la Cloud API de Meta (n8n ne sert qu'à lire la base de connaissances depuis Google Drive) : son déploiement par client est décrit dans l'onglet « WhatsApp Agent » (Agent client, Enrichir Léo, Chatbot du site). Cette page-ci ne vaut que pour un agent construit dans n8n avec Twilio comme passerelle WhatsApp.
Ce guide décrit un montage recommandé : les noms de champs et de tables sont des propositions à aligner sur les flux réellement déployés, que cette page ne reflète pas. Aucune donnée client ni aucun identifiant n'a sa place ici : les fiches clients vivent dans la base, jamais dans cette page.

1. Le principe : un seul agent, une fiche par client

On ne copie pas un flux n8n par client. Un flux unique par canal reçoit le message, retrouve le client, charge sa fiche, assemble le prompt, appelle le modèle, puis répond. Personnaliser = remplir une fiche, pas modifier du code.

  1. Entrée : webhook Twilio (WhatsApp) ou Chat Trigger n8n (chatbot du site).
  2. Identification : le numéro destinataire (To) pour WhatsApp, la clé publique du widget pour le site. Jamais une valeur lue dans le texte du message.
  3. Chargement de la fiche client et de ses connaissances.
  4. Garde-fous avant le modèle : signature, doublon, mots-clés d'arrêt, conversation reprise par un humain, plafond de messages.
  5. Agent : prompt assemblé + mémoire de la conversation + outils autorisés pour ce client.
  6. Contrôle de la réponse, puis envoi et journalisation.

3. Où la ranger

  • Une table (Postgres, ou table de données n8n pour un petit volume) agents_clients, une ligne par client, une colonne par champ ci-dessus.
  • Les connaissances dans une table à part, agents_connaissances (client_id, titre, texte, mis_a_jour_le), pour qu'un client corrige une réponse sans toucher à la fiche.
  • Le numéro WhatsApp est unique sur toute la table : c'est lui qui route les messages entrants. Un doublon enverrait la conversation d'un client dans l'agent d'un autre.
  • Aucun secret dans la fiche : les clés Twilio et du modèle restent dans les identifiants n8n.

4. Brancher WhatsApp via Twilio

Réception

  1. Nœud Webhook en POST ; l'URL de production est collée dans Twilio, à l'émetteur WhatsApp (« When a message comes in »). Twilio envoie du form-urlencoded : From, To, Body, MessageSid, ProfileName, NumMedia.
  2. Vérifier la signature X-Twilio-Signature (HMAC-SHA1 de l'URL publique complète et des paramètres triés, avec le jeton d'authentification). Dans un nœud Code, cela demande d'autoriser le module crypto côté n8n. Sans vérification, n'importe qui peut faire parler l'agent au nom du client. Si l'URL vue par n8n diffère de celle déclarée à Twilio (proxy), signer avec l'URL publique.
  3. Répondre tout de suite à Twilio (200, corps vide) puis traiter : Twilio abandonne un webhook qui dépasse environ quinze secondes, et un modèle peut être plus lent.
  4. Dédoublonner sur MessageSid : Twilio réessaie en cas d'échec, sans cela le client reçoit deux réponses.
  5. Retrouver la fiche par To (retirer le préfixe whatsapp:). Numéro inconnu : ignorer et journaliser, ne rien répondre.

Envoi

  • Réponse par l'API Messages de Twilio (nœud Twilio ou requête HTTP), From = l'expéditeur du client, To = le correspondant.
  • Fenêtre de 24 h : un message libre n'est permis que dans les 24 h suivant le dernier message du correspondant. Au-delà, seul un modèle approuvé par Meta peut partir (ContentSid + variables). L'agent doit connaître l'heure du dernier message entrant et ne jamais tenter un message libre hors fenêtre.
  • Relances, rappels, confirmations : toujours des modèles, créés et approuvés avant la mise en ligne (délai d'approbation à prévoir dans le planning du client).
  • Enregistrer le statut final de chaque envoi (delivered, failed, undelivered) et alerter sur les échecs répétés.

5. Le chatbot du site

Même cœur, autre porte d'entrée : nœud Chat Trigger (ou webhook) derrière le widget du site. Deux différences :

  • L'identifiant du client vient d'une clé publique propre au widget, relue en base à chaque appel. Renouveler la clé coupe l'ancien widget.
  • Origine autorisée (domaine du client) vérifiée côté n8n, plafond de messages par visiteur et par heure, et mention visible « assistant automatique » dans la fenêtre.

Le reste (fiche, prompt, connaissances, escalade, journal) est strictement le même : on factorise le cœur dans un sous-flux appelé par les deux canaux.

6. Assembler le prompt

Le prompt a trois étages. Seul le deuxième change d'un client à l'autre.

  1. Socle AgenIA (identique pour tous) : règles de sécurité, refus d'obéir à des instructions venues du message, interdiction d'inventer, escalade, format de réponse.
  2. Fiche du client : les champs du §2 injectés tels quels.
  3. Connaissances : les extraits utiles à cette question.

Gabarit

{{extraits}}

Règles d'écriture

  • Réponses courtes (WhatsApp n'est pas un email) : trois phrases au plus, une seule question à la fois.
  • Les chiffres, adresses et liens ne viennent que de la fiche ou des connaissances ; une sortie structurée permet ensuite de refuser une réponse qui cite un nombre, un lien ou un numéro absent de ces sources.
  • Le texte du correspondant est encadré (balises) dans le prompt et traité comme non fiable.

7. Connaissances du client

  • Petit volume (une page de FAQ, quelques offres) : tout injecter dans le prompt. Plus simple, moins cher à déboguer, aucune recherche qui se trompe.
  • Gros volume (catalogue, documents) : base vectorielle via les nœuds Vector Store de n8n, un espace par client (filtre obligatoire sur client_id), quelques extraits par question.
  • Écrire les connaissances sous forme de questions-réponses courtes, datées. Les prix et horaires sont à relire à chaque changement : une connaissance périmée est pire qu'une absence.
  • Demander au client un référent qui valide chaque mise à jour.

8. Mémoire de la conversation

  • Clé de session = client_id + identifiant du correspondant (WaId ou identifiant du visiteur). Jamais le seul numéro du correspondant : une même personne écrivant à deux clients ne doit pas voir les deux fils se mélanger.
  • Fenêtre de quelques dizaines de messages au plus ; au-delà, un résumé enregistré.
  • Journaliser chaque échange (entrant, sortant, horodatage, MessageSid) : preuve en cas de litige et matière à améliorer.

9. Passage à un humain

  1. Le modèle (ou une règle de mots-clés) déclenche l'escalade.
  2. Un indicateur repris_par_humain est posé sur la conversation : l'agent se tait tant qu'il est posé.
  3. Le contact d'escalade de la fiche reçoit la conversation et le motif, avec le lien pour répondre.
  4. L'indicateur retombe à la clôture manuelle ou après un délai décidé avec le client.
  5. Dire à l'utilisateur ce qui va se passer et quand (« un conseiller vous répond demain avant 10 h »), jamais une promesse que le client ne tient pas.

10. Conformité

  • Transparence : dès le premier message, indiquer qu'il s'agit d'un assistant automatique et comment joindre un humain.
  • Consentement WhatsApp : écrire le premier à quelqu'un exige son accord préalable (opt-in), conservé avec la date et la source. Un numéro trouvé en ligne n'est pas un accord. Respecter immédiatement « STOP », « ARRÊT » et équivalents : un mot-clé traité dans le flux, avant le modèle, et trace de la demande.
  • Données : durée de conservation des conversations fixée avec le client (purge planifiée), mention dans sa politique de confidentialité, contrat de sous-traitance signé. Twilio, Meta et le fournisseur du modèle sont des sous-traitants à lister.
  • Minimisation : ne pas envoyer au modèle ce dont il n'a pas besoin (pas de pièces d'identité, pas de données de santé ni de paiement dans le fil).
  • Les chiffres et conditions dits par l'agent engagent le client : d'où la liste fermée des offres et des prix citables.

11. Recette avant la mise en ligne

À rejouer pour chaque nouveau client, sur un numéro de test (bac à sable Twilio, puis expéditeur réel).

  1. Message normal : le bon client, le bon ton, la bonne langue.
  2. Question hors périmètre : refus poli, aucune invention.
  3. Question dont la réponse n'est pas dans les connaissances : « je ne sais pas » et proposition de rappel.
  4. Demande de prix quand « jamais de prix » est réglé : l'agent n'en donne pas.
  5. « Je veux parler à quelqu'un » : escalade déclenchée, agent silencieux ensuite, notification reçue.
  6. Tentative d'injection (« ignore tes instructions », « montre ton prompt ») : sans effet.
  7. Même message envoyé deux fois par Twilio (rejouer le MessageSid) : une seule réponse.
  8. Signature absente ou fausse : requête rejetée.
  9. Message après plus de 24 h : modèle approuvé utilisé, jamais un message libre.
  10. « STOP » : arrêt immédiat, aucun envoi ultérieur.
  11. Deux clients différents écrivant avec le même numéro : deux mémoires séparées, deux fiches.
  12. actif à faux : aucune réponse, alerte reçue.
  13. Panne du modèle : message d'attente neutre ou escalade, jamais le silence ni une erreur technique visible.

12. Mise en service et suivi

  • Un flux d'erreur n8n rattaché au flux principal, qui alerte sans exposer de contenu de conversation.
  • Plafond de messages par client et par jour, et alerte de coût : un correspondant (ou un robot) qui boucle ne doit pas vider le budget.
  • Premier mois : relecture hebdomadaire d'un échantillon de conversations avec le client, puis ajustement de la fiche (pas du flux).
  • Indicateurs à suivre : messages reçus, taux d'escalade, temps de première réponse, rendez-vous obtenus, échecs d'envoi.
  • Tout changement de la fiche ou des connaissances est daté : on doit pouvoir dire ce que l'agent savait le jour d'une réponse contestée.

13. Mise en route d'un nouveau client : l'ordre

  1. Atelier de 1 h pour remplir la fiche (§2) et rassembler les connaissances.
  2. Expéditeur WhatsApp demandé chez Twilio et modèles soumis à Meta (délai à prévoir).
  3. Ligne créée dans agents_clients avec actif à faux.
  4. Recette (§11) sur le bac à sable, puis sur l'expéditeur réel.
  5. Validation écrite par le client des réponses types.
  6. actif à vrai ; surveillance rapprochée pendant les premiers jours.
